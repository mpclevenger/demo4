# TRUST data model, v1 (22 tables)

Status: **agreed by the owner, 3 Nov 2026** (seven tables; `warning_ack` added the same day for the data quality checks; `proposal` and `proposal_decision` added 3 Nov for dictionary proposals; `itdr_application` and `dr_test` added 3 Nov to keep the ITDR application and DR tests files as tables). Replaces the 33-table design of 31 Oct 2026 (D-65, D-66), which was written before the owner's 2 Nov decisions: every file stands alone, mapping can be re-run at any time, settings live in files, every month stands alone. Most of those 33 tables would have held things TRUST now keeps another way (below).

All tables are in the Postgres add-on (`DATABASE_URL`). Without a database (a laptop, tests) the same things are kept in the `store/` folder. Migrations are in `migrations/`, append-only.

## The tables

| Table | One row per | Holds | Changes |
|---|---|---|---|
| `submission` | upload | feed, month, who (typed name), when, file name, hash of the file as received, hash of what was kept, columns kept and not found, SharePoint link | Never edited. The newest per feed and month is the one mapping uses; earlier ones are kept (D-92). |
| `kept_file` | kept file | the file cut down to what TRUST uses (HR: only the CTO's line), by the hash of what was kept | Never edited. |
| `month` | month | **Not used since 17 Nov 2026** (the month lock was removed). It held a month's status (`open` or `locked`), who locked it and the seal. Older rows are kept and never read; every month is open. No migration removes it | Never written or read. |
| `month_result` | mapping or scoring run | kind (`mapped` or `scored`), month, the full result, when, by, and the git commit and settings hash it used | Never edited. The latest run of each kind is the current one; earlier runs stay, so we can see what a month looked like before a re-score. The scored document (`doc`, jsonb) holds `blocks` and `blocks_scored` per family (was `letters` / `letters_scored`), plus `firm_blocks`, `firm_status`, `firm_capped`, `firm_blocks_scored` and `firm_trust_average` (the old average of family TRUST scores, kept for comparison; firm TRUST itself is now scored from the pooled results, owner 4 Nov 2026). |
| `published_file` | file | what the website shows: `index.html`, `data.json`, `evidence.json` | Replaced by each publish. |
| `event_log` | action | upload, map, score, publish, comment, acknowledge, proposal, decision, download, claim: who, when, which month, and a short note. A download is logged with the name given and how many rows | Never edited. |
| `warning_ack` | acknowledgement | the month, the feed, which warning (a fingerprint of its wording) and the wording, who, when, and an optional reason. It gates nothing: warnings never stop a month | Never edited. A warning whose wording changes needs acknowledging again. |
| `proposal` | proposal | a suggestion to change a metric's wording, add a new metric or retire one: kind, the metric (empty for a new one), a short title, the details as filled in, who, when | Never edited. |
| `proposal_decision` | decision | the answer to a proposal: approved, returned, declined or withdrawn, with a reason (required for returned and declined), who, when. A proposal with no decision is open, and one decision closes it | Never edited. A decision is a new row. Approving records the decision only; the dictionary and the scoring are changed separately, with the owner's agreement. |
| `itdr_application` | application, per upload | from the ITDR application file: Ref (number), Application Name (tidied), Business Product Area (may be empty), Recovery Tier (0 to 5, empty for TBC or not given) and its label (Tier 0 to Tier 5, TBC, Not given), and the upload it came from | Never edited. Written with its upload in one step; the newest upload for a month is the current list. Not scored yet (RE-01 to RE-03 are planned). |
| `dr_test` | DR test, per upload | from the DR tests file: Name (tidied, as the ITDR application file), Tier, Business Area, ITDR Lead, Type of Test (Open, Closed, TTX), what it is (DR test, or tabletop exercise for TTX) and, for a DR test, production or non-production, When, Status (Successful, or Not performed when blank), when it was last performed (a DR test's comment date, a tabletop exercise's When; only when Successful), Comments, the date read from the comment, whether the comment mentions TTX, and the upload it came from (migrations 0007, 0008) | Never edited. Written with its upload; the newest upload for a month is the current list. Linked to `itdr_application` by name at mapping, not stored. Not scored yet (RE-03 is planned). |
| `data_contract` | request to onboard a data source, or a new version of one | feed, version, provider, contact, what the file is, how often, the columns TRUST may read, the metrics it may be used for, who asked and when; status (draft, approved = formal, returned, withdrawn), who decided and when, reason (migration 0009; owner, 4 Nov 2026) | The request is never edited; the decision columns are filled in once. The highest approved version per feed is the current contract. |
| `claim` | claim | a Lost and found item (feed and the item's own reference, with the label it had when claimed), the family it is claimed for, the month it was claimed from, why, who and when; status (draft = waiting, approved, returned, withdrawn, released), who decided and when, and the reason (migration 0011; owner, 9 Nov 2026) | The request is never edited; the decision columns are filled in as the claim moves. One waiting or approved claim per item. An approved claim places the item at every later Update, including later months where the same item appears. Retention never removes claims. |
| `thing` | person, team, application, ITDR application or repository, per month | the things the month's files name: kind, its own reference (SAM_ACCOUNT, app ID, ITDR Ref, repo name; a team's starts with `family:`, `department:`, `l3:` or `l4:`), the name people read, and a few facts (migration 0012; owner, 15 Nov 2026) | Replaced by every mapping run of its month. Any month can be mapped again (no month lock). |
| `thing_link` | connection between two things, per month | from, to, what the connection is (reports to, member of, placed with, owned by, serves, same as), **how it was made** in plain words (HR reporting line, repo owner, app inventory, a close name match, an approved claim) and, for a name match, how close | As `thing`. |
| `setting_change` | changed setting, per save | the audit trail of tolerance thresholds and caps changed on the site: which setting (named as in `config/thresholds.json`), the value before and after, who, when and why (migration 0013; owner, 15 Nov 2026) | Never edited. The newest row for a setting is the value in use; a setting with no row uses the file's value. |
| `comment` | comment | month, family, metric or building block (empty = the whole family; column `comment.block`), kind (explanation, data query, action), text, who, when, the comment it replies to, status for queries and actions (open, answered, closed). The column `after_lock` is kept from the lock days and no longer written | Never edited. A reply is a new row; a thread's status is its latest row's. |
| `metric_intake` | metric a team wants on the scorecard | the short ID (`MI-001`...), the stage (Wanted, In progress or Measured), the details as filled in (`fields`: name, what it tells leadership, building block, provider team, contact, system and, for In progress, the data contract), who added it and when, who changed it last and when (migration 0014; owner, 15 Nov 2026) | Changed in place by Tech Risk, but every change also adds a row to `metric_intake_history`. Creates no metric and changes no score. |
| `metric_intake_history` | change to a metric intake record | the record's ID, when, who, what happened (added, changed or moved), an optional note, and the fields before and after (migration 0014) | Never edited or removed. |
| `metric_value_send` | send of numbers for a record | the record's ID, the month (YYYY-MM), the shape (`totals` = one row per team, `items` = one row per item), when, who sent it (the service account), how many rows were kept and set aside, the rows kept, the rows set aside with the reason for each, and the count and total per team (migration 0014) | Never edited. The newest send for a record and month is the one shown; earlier ones are kept. Nothing here is scored. |
| `risk_answer` | saved answer to one question for one group | the group (as named in `config/risk_groups.json`), the question (by the name its driver rule reads, such as `RD01`), the answer (yes, no or the number as typed; empty = cleared), who saved it, when, and whether a signed-in Tech Risk person saved it (migration 0015; owner, 15 Nov 2026) | Never edited. A changed answer is a new row; the newest row of a question is the answer in use. |
| `risk_assessment` | Submit of a group's Risk form | the group, who submitted, when, and the result (`result`, jsonb): the answers used, the rating settings used, which drivers were on, off or not known, and each risk's rating with its steps and its trend since the previous assessment (migration 0015) | Never edited or removed. Every Submit is a new assessment and all are kept. |

`thing` and `thing_link` are the first layer of the **shared core** ([doc 18](18_shared_core.md)): they hold what mapping decided, in rows other layers can point at. Any grouping (product family, department, L3, L4) is a roll-up of `member_of` links.

## Rules

- **Comments never change a score.** They sit beside the results. The page reads them live, so a new comment shows without publishing again.
- **No month lock (owner, 17 Nov 2026).** Every month is always open: upload, map, score, update and publish work for any month at any time. Updating a month re-reads its newest files with the current settings. There is no seal and no reopen. Older databases may still hold a month marked `locked`, a seal and `lock` or `reopen` events; they stay as history and are ignored.
- **Who.** Anyone who gets past the company's access add-on can upload, update and comment (owner, 3 Nov 2026). They type their name, which is recorded on every row.

## Querying results

Results are stored as one document per run, which keeps the model small but makes questions like "every Red SE-05 across all months" harder in SQL. If Tech Risk or the auditors want that, add a read-only view over `month_result` that looks like a table; nothing else has to change.
